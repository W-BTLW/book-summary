# 인증과 인가
### 인증 : 사용자가 누구인지 확인하는 과정
### 인가 : 사용자에게 자원에 접근할 수 있는 권한을 부여

<br/>

### 토큰
1. 별도 저장소에 토큰과 사용자 식별자 정보 저장
   - DB나 레디스같은 별도 저장소에 토큰 정보를 저장
   - 토큰, 사용자 식별자, 생성 시간, 최근 사용시간, 그 외 유효시간, 클라이언트 버전 등 추가 데이터
   - 토큰 데이터는 크기가 글케 크지 않음
   - 메모리에 저장하는 방식의 단점을 커버 가능

2. 메모리에 토큰 저장
   - 서버를 재시작하면 토큰 데이터가 사라짐
   - 생성할 수 있는 세션 개수가 메모리 크기에 제한을 받음

3. 토큰 자체에 사용자 식별자 정보를 저장
   - JWT
   - 토큰만 있으면 사용자가 누구인지 확인할 수 있음
   - 별도 외부 DB에 토큰데이터를 저장할 필요가 없으니 구조가 간단
   - 메모리 저장 아니어서 수평확장 쉬움
   - 네트워크 트래픽이 증가한다는 단점이 있음 -> 최소한의 데이터만 담아야 함
   - 토큰 데이터를 서버에서 제어할 수 없음 -> 서버에서 삭제하거나 변경할 수 없음

</br>

### 토큰 송수신 방법
1. 쿠키 : 쿠키를 사용해서 세션ID 주고받음
2. 헤더 : 헤더에 Token, X-0token, Auth 등 특정 헤더로 토큰값 구분

</br>

### 토큰 보안
1. 토큰 유효시간에 제한 + 클라이언트IP 비교
2. 토큰을 무효화해서 강제로 로그아웃 시키는 기능이 필요


</br>

# 데이터 암호화
1. 단방향 암호화
   - 암호화한 데이터를 복호화 할 수 없는 암호화 방식
   - 해시 함수를 사용해서 데이터를 해시 값으로 변환 (Ex. SHA-256, MD5, BCrypt)
   - 바이트 배열을 기준으로 암호화
   - 사용자가 비밀번호를 잊었을 때 기존 비밀번호를 알려주지 못함. 임의의 문자열로 초기화
   - 취약점을 보완하기 위해 '솔트' 사용. 암호화할 때 마다 결과 해시 값이 달라짐
  
2. 양방향 암호화
   - 암복호화 모두 가능
   - SSH 프로토콜, API호출 시 사용하는 HTTPS처럼 보안이 중요한 데이터 송수신 과정에서 주로 사용
   - Ex. AES, RSA, 
     - AES
     - RSA
     - HMAC : 비밀 키만 공유하면 정해진 해시 알고리즘을 이용해서 MAC을 생성할 수 있기 때문에 낮은 비용으로 인증 보안을 구현할 수 있다. 그러나, 비밀키가 외부에 유출되면 보안에 취약해진다.
   - 대칭키와 비대칭키
     - 대칭키 : 암복호화할 때 동일한 키 사용. 키 보안이 매우 중요
     - 비대칭키 : 암복호화할 때 서로 다른 키 사용. 공개키로 암호화, 개인 키로 복호화
   
</br>

# HMAC을 이용한 데이터 검증
HMAC(Hash-based Message Authentication), 메시지의 무결성과 인증을 보장하기 위해 사용하는 암호화 기술
- 발신자 : 메시지와 키를 이용해서 생성한 MAC을 메시지와 함께 전송
- 수신자 : 메시지와 키를 이용해서 생성한 MAC과 발신자가 보낸 MAC이 같은지 비교

발신자와 수신자가 비밀 키만 공유하면 정해진 해시 알고리즘을 이용해서 MAC을 생성할 수 있기 때문에 낮은 비용으로 인증보안 구현 가능
사용되는 해시 알고리즘에 따라 보안성도 향상
but, 비밀키가 외부에 유출되면 보안이 취약해짐.

</br>

# 방화벽으로 필요한 트래픽만 허용하기
- 인바운드/아웃바운드 모두 필수 트래픽만 허용하고 나머지는 차단 권고
- 단순 트래픽 제어 외에도 DDoS나 포트 스캔 같은 네트워크 공격을 차단하는 기능을 제공
- SQL 인젝션, XSS 같은 웹 기반 위협도 감지하고 차단


</br>
