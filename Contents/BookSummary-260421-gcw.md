# ⚙️ 동시성 제어와 잠금 전략 정리

## 1. 서버의 동시 요청 처리 방식

서버가 동시에 여러 클라이언트 요청을 처리하는 방식은 크게 두 가지가 있다.

### 🔹 요청당 스레드 방식 (THREAD PER REQUEST)

- 클라이언트 요청마다 스레드를 생성하여 처리하는 방식
- 구조가 단순하고 이해하기 쉬움
- 요청 수 증가 시 스레드 수도 함께 증가

---

### 🔹 비동기 / 논블로킹 I/O (ASYNC / NON-BLOCKING I/O)

- 소수의 스레드로 여러 요청을 처리하는 방식
- 이벤트 기반으로 동작
- 스레드 수를 일정하게 유지하면서 많은 요청 처리 가능

---

### 🔹 처리 방식 비교

| 구분 | 요청당 스레드 방식 | 비동기 / 논블로킹 I/O |
|------|------------------|------------------------|
| 구조 | 단순 | 복잡 |
| 스레드 수 | 요청 수만큼 증가 | 소수 유지 |
| 메모리 사용 | 많음 | 적음 |
| 확장성 | 낮음 | 높음 |
| 구현 난이도 | 쉬움 | 어려움 |

---

## 2. 동시성 문제

### 🔹 경쟁 상태 (RACE CONDITION)

- 여러 스레드가 동시에 공유 자원에 접근할 때  
- 접근 순서에 따라 결과가 달라지는 상황

➡️ 문제점  
- 데이터 불일치  
- 예측 불가능한 결과 발생  

---

## 3. 잠금을 이용한 동시 접근 제어

### 🔹 기본 개념

- 공유 자원에 대해 동시에 하나의 스레드만 접근하도록 제한
- 다른 스레드는 잠금이 해제될 때까지 대기

---

### 🔹 MUTEX (뮤텍스)

- 상호 배제(MUTUAL EXCLUSION) 기반 잠금
- 한 번에 하나의 스레드만 접근 가능

---

### 🔹 SEMAPHORE (세마포어)

- 동시에 실행 가능한 스레드 수를 제한
- 퍼밋(PERMIT) 기반으로 동작

---

### 🔹 LOCK 계열 비교

| 구분 | MUTEX | SEMAPHORE |
|------|------|-----------|
| 접근 허용 수 | 1개 | N개 |
| 목적 | 상호 배제 | 동시 실행 제한 |
| 사용 난이도 | 낮음 | 중간 |
| 사용 사례 | 공유 변수 보호 | 자원 수 제한 |

---

### 🔹 ATOMIC TYPE

- 잠금을 사용하지 않고도 원자적 연산 보장
- CAS 기반으로 동작
- 스레드를 블로킹하지 않음

---

### 🔹 ATOMIC vs LOCK 비교

| 구분 | ATOMIC | LOCK |
|------|--------|------|
| 방식 | CAS 기반 | 스레드 블로킹 |
| 성능 | 매우 빠름 | 상대적으로 느림 |
| 대기 | 없음 | 있음 |
| 사용 범위 | 단순 연산 | 복잡 로직 |
| 안정성 | 제한적 | 높음 |

---

### 🔹 동시성 지원 컬렉션

- 멀티스레드 환경에서 안전하게 사용 가능한 컬렉션
- 내부적으로 동기화 처리

---

### 🔹 일반 컬렉션 vs 동시성 컬렉션

| 구분 | 일반 컬렉션 | 동시성 컬렉션 |
|------|------------|---------------|
| 스레드 안전성 | 없음 | 있음 |
| 성능 | 단일 스레드에 최적 | 멀티 스레드에 최적 |
| 사용 환경 | 단일 스레드 | 멀티 스레드 |

---

## 4. DB와 동시성 제어

### 🔹 선점 잠금 (PESSIMISTIC LOCK)

- 데이터를 수정하기 전에 잠금을 먼저 획득
- 다른 트랜잭션은 대기

---

### 🔹 비선점 잠금 (OPTIMISTIC LOCK)

- 잠금을 사용하지 않고 값 비교로 충돌 처리
- 충돌 발생 시 업데이트 실패

---

### 🔹 선점 vs 비선점 잠금 비교

| 구분 | 선점 잠금 | 비선점 잠금 |
|------|----------|-------------|
| 방식 | LOCK 선점 | 값 비교 |
| 충돌 처리 | 사전 방지 | 사후 감지 |
| 성능 | 낮음 | 높음 |
| 충돌 많을 때 | 유리 | 불리 |
| 충돌 적을 때 | 비효율 | 매우 효율 |

---

### 🔹 분산 잠금 (DISTRIBUTED LOCK)

- 여러 서버(프로세스) 간 동시 접근 제어
- 공통 자원 보호 목적

---

### 🔹 로컬 잠금 vs 분산 잠금

| 구분 | 로컬 잠금 | 분산 잠금 |
|------|----------|----------|
| 범위 | 단일 프로세스 | 여러 서버 |
| 구현 난이도 | 낮음 | 높음 |
| 사용 기술 | LOCK, SYNCHRONIZED | REDIS, ZOOKEEPER |
| 목적 | 내부 동기화 | 서버 간 동기화 |

---

## 5. 잠금 사용 시 주의사항

### 🔹 DEADLOCK (교착 상태)

- 서로가 가진 LOCK을 기다리며 무한 대기 상태

---

### 🔹 STARVATION (기아 상태)

- 특정 스레드가 자원을 계속 얻지 못하는 상태

---

### 🔹 문제 상황 비교

| 구분 | DEADLOCK | STARVATION |
|------|----------|------------|
| 정의 | 서로 LOCK 대기 | 특정 스레드 실행 못함 |
| 원인 | 순환 대기 | 우선순위 불균형 |
| 해결 | 순서 통일, 타임아웃 | 공정성 보장 |

---

## 6. 언제 어떤 방법을 선택할까?

### 🔹 상황별 선택 기준

- 단순 연산 → ATOMIC  
- 공유 데이터 보호 → LOCK  
- 동시 처리 수 제한 → SEMAPHORE  
- 충돌 많음 → 선점 잠금  
- 충돌 적음 → 비선점 잠금  
- 여러 서버 환경 → 분산 잠금  

---

### 🔹 최종 정리

- **간단 + 빠른 처리 → ATOMIC**
- **정합성 중요 → LOCK**
- **성능 중심 → OPTIMISTIC LOCK**
- **분산 환경 → DISTRIBUTED LOCK**

👉 핵심은 "정합성 vs 성능 vs 확장성"의 균형이다.
