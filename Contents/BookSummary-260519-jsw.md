# 네트워크 IO

DB는 TCP를 통해 데이터를 주고 받는다.

데이터를 주고 받는 동안 스레드는 데이터 전송이 완료될 때까지 대기한다. 즉, 스레드가 블로킹된다.

입출력에 소요되는 시간은 코드를 실행하는 시간보다 **훨씬**길다(많게는 90% 이상).

IO 대기와 컨텍스트 스위칭이 늘어나면 CPU 효율(사용률)이 낮아지고 스레드가 늘어나면 메모리 점유가 많아진다.

이 때 스케일 아웃 혹은 스케일 업이 불가능하다면 다음 두가지 고려할 수 있다.

## 경량스레드(가상스레드 혹은 고루틴)

경량스레드는 OS 레벨의 스레드(플랫폼스레드)가 아니다. JVM같은 런타임이 관리(스케줄)하는 스레드다.

플랫폼스레드보다는 적은 자원을 사용하는데 예를 들면 경량스레드는 2KB 수준이고 플랫폼스레드는 1MB 수준의 차이.

우리가 작성하는 소스 코드는 크게 IO 중심 작업과 CPU 중심 작업으로 나눌 수 있는데

CPU 중심 작업에 가상스레드를 적용한다 한들 성능개선 효과를 얻을 수 없다.

*가상스레드는 외부 응답을 기다리는 대기시간을 효율적으로 처리할 수 있는 기술이지만
CPU 계산 자체를 빠르게 하거나 하지는 않기 때문이다.*

IO 중심 작업이라고 무조건 가상스레드의 이점을 얻는 것도 아니다.

가상스레드는 처리량을 높일 수 있는데 언급된 내용과 비슷한 맥락으로, 실행 속도가 빨라지는 것은 기대할 수 없다.

가상스레드는 생성 비용이 적어서 미리 스레드 풀을 구성할 필요는 없다.

기존 소스를 크게 바꾸지 않고 적용할 수 있어서 손쉽게 성능 이점을 가져갈 수 있다.

## 논블로킹 or 비동기 IO

경량스레드로 한계가 오면 논블로킹 IO를 고민할 수 있다.

논블로킹 IO는 입출력이 끝날 때까지 스레드가 대기하지 않는다.

일반적으로 블로킹 IO로 구현한 서버는 커넥션별(또는 요청별)로 스레드를 할당한다.

반면 논블로킹 IO는 클라이언트 수 상관 없이 소수의 스레드를 사용(같은 메모리로 더 많은 클라이언트 연결을 처리)한다.

만약, 성능 문제가 없다면 구현 변경을 고민하지 말아야한다.
