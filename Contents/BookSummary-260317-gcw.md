# 비동기 연동 방식 정리

시스템 간 연동은 반드시 동기 방식으로 처리할 필요는 없으며  
**비동기 방식으로도 다양한 구조를 통해 구현할 수 있다.**

대표적인 방식은 다음과 같다.

- 별도 스레드 실행
- 메시징 시스템 이용
- 트랜잭션 아웃박스 패턴
- 배치 연동
- CDC(Change Data Capture)

---

# 1. 별도 스레드 실행

가장 단순한 비동기 처리 방식이다.

Spring 환경에서는 다음과 같이 구현할 수 있다.

```
@Async
```

해당 어노테이션을 사용하면 별도의 스레드에서 작업이 수행된다.

## 특징

- 구현이 비교적 간단하다
- 동일 애플리케이션 내부에서 비동기 처리 가능

## 주의사항

비동기 실행 시 **예외 처리에 반드시 유의해야 한다.**

별도 스레드에서 실행되는 로직은  
상위 트랜잭션이나 호출 스택으로 예외가 전달되지 않기 때문에  
**연동 과정에서 발생한 오류를 내부에서 직접 처리해야 한다.**

예를 들어

- 오류 로그 기록
- 재시도 처리
- 실패 상태 기록

등을 직접 구현해야 한다.

---

# 2. 메시징 시스템 이용

메시징 시스템은 **시스템 간 데이터 전달을 위한 매개체 역할**을 한다.

메시지를 통해 시스템 간 결합도를 낮출 수 있으며  
대규모 시스템에서 매우 많이 사용되는 방식이다.

## 특징

- 시스템 간 결합도 감소
- 메시지 처리량을 통해 부하 조절 가능
- 수신 시스템 추가가 용이

예를 들어 새로운 시스템이 메시지를 받아야 하는 경우  
**메시징 시스템의 Consumer만 추가하면 된다.**

## Producer / Consumer

메시징 시스템에서는 일반적으로 다음과 같이 구분한다.

- **Producer** : 메시지를 보내는 시스템
- **Consumer** : 메시지를 수신하는 시스템

---

# 2.1 Kafka

대규모 데이터 처리 환경에서 많이 사용되는 메시징 시스템이다.

## 특징

- 초당 **백만 건 이상의 메시지 처리 가능**
- **수평 확장이 매우 용이**
- 메시지를 **파일 형태로 저장**하여 유실 가능성이 낮음
- Consumer가 **메시지를 언제든지 재처리 가능**

대규모 로그 처리나 이벤트 스트리밍 환경에서 많이 사용된다.

---

# 2.2 RabbitMQ

전통적인 메시지 큐 시스템 중 하나이다.

## 특징

- 클러스터 구성을 통해 처리량 확장 가능
- Kafka 대비 **더 많은 자원을 요구**
- **큐에 등록된 순서대로 메시지 처리**
- 메시지 **수신 여부 확인(ACK)** 기능 제공

업무 처리 흐름이 **순서 보장이 필요한 경우** 많이 사용된다.

---

# 2.3 Redis

Redis는 메모리 기반 시스템으로 메시징에도 활용될 수 있다.

## 특징

- **메모리 기반이므로 지연 시간이 매우 짧음**
- RabbitMQ 대비 **높은 처리량 가능**
- Pub/Sub 기반 메시징 지원

## 단점

- 구독자가 없으면 **메시지가 유실됨**
- **영구 메시지 저장 기능 없음**

따라서 Redis 메시징은 **실시간 이벤트 처리**에 적합하다.

---

# 메시지 처리 시 고려사항

메시지 시스템을 사용할 때는 **메시지 유실 및 오류 처리 전략**을 반드시 고려해야 한다.

대표적인 처리 방식은 다음과 같다.

| 처리 방식 | 설명 |
|---|---|
| 무시 | 메시지 유실을 허용 |
| 재시도 | 실패 시 재전송 (중복 메시지 처리 고려 필요) |
| 실패 기록 | 실패 로그만 남기고 처리 종료 |

또한 **DB 트랜잭션 완료 이후 메시지를 전송하는 것이 중요하다.**

트랜잭션이 롤백되었는데 메시지가 먼저 전송되면  
**데이터 불일치 문제가 발생할 수 있기 때문이다.**

---

# 메시지 유형

메시지는 크게 두 가지 유형으로 구분된다.

## 이벤트(Event)

어떤 일이 발생했음을 알리는 메시지

예시

```
주문이 생성됨
회원이 가입됨
결제가 완료됨
```

## 커맨드(Command)

특정 작업 수행을 요청하는 메시지

예시

```
주문 처리 요청
결제 실행 요청
배송 시작 요청
```

# 3. 트랜잭션 아웃박스 패턴

트랜잭션 아웃박스 패턴은  
**메시지 유실을 방지하기 위한 패턴**이다.

메시지를 바로 전송하지 않고  
**DB의 Outbox 테이블에 저장한 뒤 전송한다.**

## 구조

1. 비즈니스 데이터 저장
2. Outbox 테이블에 메시지 기록
3. 별도 프로세스가 Outbox 메시지 전송

## 장점

- DB 트랜잭션과 메시지 전송을 **동기화 가능**
- 메시지 유실 방지
- 메시지 상태 모니터링 가능

Outbox 테이블에는 보통 다음 컬럼이 존재한다.

| 컬럼 | 설명 |
|---|---|
| message_id | 메시지 식별자 |
| payload | 메시지 데이터 |
| status | 전송 상태 |
| created_at | 생성 시간 |

특히 **전송 상태 컬럼을 두면 메시지 처리 여부를 쉽게 확인할 수 있다.**

---

# 4. 배치 기반 연동

배치 방식은 **대량 데이터 연동에 적합한 방식**이다.

## 전형적인 배치 처리 과정

1. DB에서 전송할 데이터 조회
2. 조회 결과를 파일로 생성
3. 파일 시스템 또는 외부 시스템으로 전송

## 특징

- 대량 데이터 처리에 유리
- 시스템 부하를 특정 시간에 집중 가능

파일 대신 **API를 이용하여 데이터를 일괄 전송하는 방식**도 사용된다.

또한 운영 편의를 위해  
**배치 실패 시 재시도를 수행할 수 있는 API를 구현하는 것이 유리하다.**

---

# 5. CDC (Change Data Capture)

CDC는 **데이터 변경을 감지하여 다른 시스템으로 전달하는 방식**이다.

## 정의

> 변경된 데이터를 추적하고 판별하여  
> 해당 변경 데이터를 기반으로 작업을 수행할 수 있도록 하는  
> 소프트웨어 설계 패턴

## 동작 과정

1. DB에서 INSERT / UPDATE / DELETE 발생
2. DB가 변경 데이터를 CDC 처리기에 전달
3. CDC 처리기가 데이터를 가공
4. 다른 시스템으로 전파

## 전달 방식

CDC 처리 이후 데이터 전달 방식은 다음과 같다.

- 메시지 시스템 전달 (Kafka 등)
- DB → DB 복제
- 이벤트 기반 처리

## 장점

- 애플리케이션 수정 없이 데이터 변경 감지 가능
- 실시간 데이터 동기화 가능

---

# 정리

비동기 연동 방식은 시스템 규모와 목적에 따라 다양한 방식으로 구현할 수 있다.

| 방식 | 특징 |
|---|---|
| 별도 스레드 | 구현 간단 |
| 메시징 시스템 | 대규모 시스템에 적합 |
| 트랜잭션 아웃박스 | 메시지 유실 방지 |
| 배치 연동 | 대량 데이터 처리 |
| CDC | 데이터 변경 기반 연동 |

대규모 시스템에서는  
**메시징 + 아웃박스 + CDC 조합 구조가 많이 사용된다.**
