# 인증(Authentication)과 인가(Authorization)

## 1. 인증과 인가의 차이

### 인증(Authentication)
사용자가 누구인지 확인하는 과정이다.

예시
- 아이디/비밀번호 로그인
- OTP 인증
- 생체 인증(지문, 얼굴 인식)

### 인가(Authorization)
인증된 사용자에게 특정 자원에 접근할 수 있는 권한을 부여하는 과정이다.

예시
- 일반 사용자는 게시글 조회만 가능
- 관리자는 회원 정보 수정 및 삭제 가능

즉,

- 인증(Authentication) → "너는 누구인가?"
- 인가(Authorization) → "무엇을 할 수 있는가?"

---

## 2. 토큰 기반 사용자 식별 방식

사용자를 식별하기 위해 일반적으로 토큰(Token)을 사용한다.

대표적으로 다음 두 가지 방식이 존재한다.

### 2.1 서버 저장소 기반 방식

서버가 별도의 저장소에 토큰과 사용자 정보를 저장하는 방식이다.

저장 가능한 위치

- DB(Database)
- Redis
- 서버 메모리(Session)

#### 특징

사용자가 로그인하면 서버가 토큰을 생성하고 저장소에 보관한다.

```text
사용자
   ↓
로그인
   ↓
서버
   ↓
토큰 생성
   ↓
DB / Redis / Session 저장
```

이후 사용자가 요청할 때 토큰을 전달하면 서버는 저장소에서 토큰을 조회하여 사용자를 식별한다.

#### 장점

- 서버가 토큰을 직접 관리할 수 있다.
- 강제 로그아웃이 쉽다.
- 토큰 폐기가 쉽다.

#### 단점

- 저장소 관리 비용이 발생한다.
- 세션을 메모리에 저장할 경우 서버 재시작 시 데이터가 사라질 수 있다.
- 세션 수는 서버 메모리 크기에 영향을 받는다.
- 여러 대의 서버를 사용할 경우 세션 공유 또는 Sticky Session(고정 세션)이 필요하다.

---

### 2.2 토큰 자체에 사용자 정보를 저장하는 방식

토큰 내부에 사용자 식별 정보를 포함하는 방식이다.

대표적인 예가 JWT(JSON Web Token)이다.

사용자가 로그인하면 서버는 사용자 정보를 포함한 JWT를 생성하여 클라이언트에게 전달한다.

```text
사용자
   ↓
로그인
   ↓
서버
   ↓
JWT 생성
   ↓
클라이언트 저장
```

이후 요청 시 JWT만 전달하면 서버는 토큰을 검증하여 사용자를 식별할 수 있다.

#### 장점

- 별도 저장소 조회가 필요 없다.
- 서버 확장이 쉽다.
- Stateless 구조 구현이 가능하다.

#### 단점

- 토큰 크기만큼 네트워크 트래픽이 증가한다.
- 발급된 토큰을 서버에서 직접 제어하기 어렵다.
- 강제 로그아웃 및 토큰 폐기가 상대적으로 어렵다.

---

## 3. 토큰 전달 방식

클라이언트와 서버는 주로 다음 두 가지 방법으로 토큰을 주고받는다.

### 3.1 Cookie 방식

토큰을 쿠키에 저장하여 자동으로 전송하는 방식이다.

```http
Cookie: accessToken=xxxxx
```

#### 장점

- 브라우저가 자동으로 전송한다.
- 구현이 편리하다.

#### 단점

- CSRF 공격에 주의해야 한다.

### CSRF(Cross-Site Request Forgery)

CSRF는 사용자가 로그인된 상태를 악용하여 사용자가 의도하지 않은 요청을 서버에 보내게 만드는 공격이다.

주로 Cookie 기반 인증 방식에서 발생하며, 브라우저가 쿠키를 자동으로 전송하는 특성을 이용한다.

예시)

사용자가 은행 사이트에 로그인한 상태에서 악성 사이트에 접속하면,

```text
사용자 → 악성 사이트 접속
       ↓
브라우저가 은행 쿠키 자동 전송
       ↓
은행 서버는 정상 사용자 요청으로 인식
---

### 3.2 Header 방식

HTTP 헤더를 이용하여 토큰을 전달한다.

대표적으로 Authorization 헤더를 사용한다.

```http
Authorization: Bearer xxxxx
```

#### 장점

- REST API에서 가장 많이 사용된다.
- CSRF 위험이 상대적으로 낮다.

#### 단점

- 클라이언트에서 직접 관리해야 한다.

---

## 4. 토큰 유효 시간 관리

토큰 만료 방식은 크게 두 가지가 있다.

### 4.1 생성 시점 기준 만료

토큰 생성 시점부터 일정 시간이 지나면 만료된다.

예시

```text
발급 시간 : 10:00
만료 시간 : 11:00
```

사용 여부와 관계없이 11시에 만료된다.

---

### 4.2 마지막 접근 시간 기준 만료

사용자가 마지막으로 접근한 시간을 기준으로 만료 시간을 갱신한다.

예시

```text
현재 만료 시간 : 11:00

10:50 요청 발생
→ 만료 시간 11:50으로 갱신
```

---

### 보안 강화를 위한 방법

- 로그아웃 기능 제공
- 토큰 강제 무효화
- 블랙리스트 관리
- Refresh Token 사용

---

## 5. Access Token과 Refresh Token

### Access Token

사용자가 인증된 사용자임을 증명하기 위한 토큰이다.

특징

- 요청 시마다 사용
- 일반적으로 짧은 만료 시간 사용
- 탈취 시 위험성이 있음

---

### Refresh Token

Access Token 재발급을 위한 토큰이다.

특징

- 로그인 상태 유지
- Access Token 만료 시 재발급
- 일반적으로 긴 만료 시간 사용

```text
로그인
 ↓
Access Token 발급
Refresh Token 발급

Access Token 만료
 ↓
Refresh Token 사용
 ↓
새로운 Access Token 발급
```

# 데이터 암호화

## 1. 단방향 암호화(Hash)

해시 함수를 이용하여 데이터를 고정 길이의 해시값으로 변환하는 방식이다.

특징

- 복호화 불가능
- 동일한 입력은 동일한 해시값 생성
- 비밀번호 저장에 주로 사용

대표 알고리즘

- SHA-256
- SHA-512
- bcrypt
- Argon2

※ MD5와 SHA-1은 현재 보안상 권장되지 않는다.

---

### 해시 활용 예시

```text
password123
 ↓
SHA-256
 ↓
A665A45920422F...
```

서버는 원본 비밀번호 대신 해시값을 저장한다.

---

### Salt

Salt는 해시 계산 전에 추가하는 임의의 값이다.

```text
원본 비밀번호
password123

Salt
ABCD1234

결합
password123ABCD1234

해시
SHA-256(...)
```

#### Salt를 사용하는 이유

동일한 비밀번호라도 서로 다른 해시값을 생성할 수 있다.

이를 통해

- 레인보우 테이블 공격 방지
- 해시값 탈취 위험 감소

효과를 얻을 수 있다.

---

## 2. 양방향 암호화

암호화와 복호화가 모두 가능한 방식이다.

대표 사용 사례

- HTTPS
- SSH
- AES
- RSA

---

### 2.1 대칭키 암호화

암호화와 복호화에 동일한 키를 사용한다.

대표 알고리즘

- AES

```text
암호화 키
     ↓
데이터 암호화
     ↓
암호문
     ↓
같은 키
     ↓
복호화
```

#### 장점

- 속도가 빠르다.
- 대용량 데이터 처리에 적합하다.

#### 단점

- 키 공유가 어렵다.
- 키가 노출되면 보안이 무너진다.

---

### 2.2 비대칭키 암호화

암호화와 복호화에 서로 다른 키를 사용한다.

사용하는 키

- 공개키(Public Key)
- 개인키(Private Key)

대표 알고리즘

- RSA

```text
공개키
  ↓
암호화
  ↓
암호문
  ↓
개인키
  ↓
복호화
```

#### 장점

- 키 공유가 쉽다.
- 보안성이 높다.

#### 단점

- 대칭키보다 속도가 느리다.

---

### AES와 IV

AES는 일반적으로 Key와 IV(Initialization Vector)를 함께 사용한다.

#### IV를 사용하는 이유

같은 데이터를 같은 Key로 암호화하면 결과가 반복될 수 있다.

이를 방지하기 위해 IV를 사용한다.

```text
평문 + Key + IV
       ↓
암호화
       ↓
암호문 생성
```

IV가 달라지면 동일한 데이터라도 다른 암호문이 생성된다.

이를 통해 패턴 분석 공격 위험을 줄일 수 있다.

---

# HMAC을 이용한 데이터 검증

## 1. HMAC이란?

HMAC(Hash-based Message Authentication Code)은

- 데이터 무결성(Integrity)
- 발신자 인증(Authentication)

을 보장하기 위한 기술이다.

HMAC은 해시 함수와 비밀키(Secret Key)를 함께 사용한다.

---

## 2. HMAC 동작 방식

발신자와 수신자는 동일한 비밀키를 공유한다.

### 발신자

```text
메시지
 +
비밀키
 ↓
HMAC 생성
 ↓
메시지 + HMAC 전송
```

### 수신자

```text
수신 메시지
 +
비밀키
 ↓
HMAC 재생성
 ↓
전달받은 HMAC과 비교
```

값이 같으면

- 메시지가 변경되지 않았음
- 올바른 발신자가 보냈음

을 확인할 수 있다.

---

## 3. HMAC의 장점

### 무결성 보장

전송 중 데이터가 변경되면 HMAC 값이 달라진다.

### 발신자 인증

비밀키를 가진 사용자만 올바른 HMAC을 생성할 수 있다.

### 효율성

공개키 암호화보다 연산 비용이 적고 빠르다.

---

## 4. 활용 사례

- API 요청 검증
- 결제 데이터 검증
- Webhook 검증
- 금융권 전문(Message) 검증
- 시스템 간 데이터 위변조 방지

---

## 정리

| 구분 | 특징 | 대표 기술 |
|--------|--------|--------|
| 인증(Authentication) | 사용자가 누구인지 확인 | 로그인, OTP |
| 인가(Authorization) | 접근 권한 부여 | Role, Permission |
| 단방향 암호화 | 복호화 불가능 | SHA-256, bcrypt |
| 양방향 암호화 | 복호화 가능 | AES, RSA |
| 대칭키 | 동일한 키 사용 | AES |
| 비대칭키 | 공개키/개인키 사용 | RSA |
| HMAC | 무결성 및 인증 보장 | HMAC-SHA256 |
| Access Token | 사용자 인증용 | JWT |
| Refresh Token | Access Token 재발급 | JWT |
