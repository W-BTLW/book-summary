# 소프트웨어 아키텍처 및 디자인 패턴 정리

## 1. MVC 패턴

MVC(Model-View-Controller)는 애플리케이션을 **모델, 뷰, 컨트롤러**의 세 영역으로 분리하는 패턴임.

* **Model**

  * 비즈니스 영역의 로직 및 데이터 처리를 담당함.
  * 애플리케이션의 핵심 기능을 구현함.

* **View**

  * 사용자에게 보여줄 결과를 생성하고 응답하는 역할을 담당함.
  * Model의 처리 결과를 사용자가 확인할 수 있는 형태로 표현함.

* **Controller**

  * 사용자의 입력을 전달받고 애플리케이션의 흐름을 제어함.
  * 요청에 따라 필요한 Model을 호출하고 처리 결과를 View로 전달함.

MVC 패턴을 사용하면 각 영역의 역할을 분리할 수 있어 기능 수정 및 유지보수가 용이함.

## 2. 계층형 아키텍처(Layered Architecture)

계층형 아키텍처는 애플리케이션의 기능을 역할에 따라 여러 계층으로 분리하는 구조임.

**하위 계층은 상위 계층에 대한 의존성을 가지지 않으며, 상위 계층에서 하위 계층으로의 의존성만 허용함.**

웹 애플리케이션에서는 통상적으로 다음과 같은 4개의 계층으로 구성함.

### 표현/UI 계층

사용자의 요청을 받아 응용 계층으로 전달하고, 처리 결과를 사용자에게 표현함.

### 응용 계층

사용자의 요청을 실질적으로 처리하는 영역임.
필요한 도메인 기능을 호출하고 전체적인 작업 흐름을 제어함.

### 도메인 계층

애플리케이션의 핵심 비즈니스 규칙과 로직을 구현함.

### 인프라스트럭처 계층

DB, 외부 API, 메시징 시스템 등 외부 시스템과의 연동을 담당함.

일반적으로 다음과 같은 흐름으로 요청을 처리함.

```text
사용자 요청
    ↓
표현/UI 계층
    ↓
응용 계층
    ↓
도메인 계층
    ↓
인프라스트럭처 계층
    ↓
처리 결과 반환
    ↓
표현/UI 계층
    ↓
사용자 응답
```

## 3. DDD(Domain-Driven Design)

DDD(Domain-Driven Design)는 **도메인 중심으로 소프트웨어를 설계하는 방법론**임.

비즈니스의 핵심 개념과 규칙을 소프트웨어 모델에 반영하는 것을 중요하게 생각하며, 대표적인 구성요소는 다음과 같음.

### Entity

고유한 식별자를 가지는 객체임.

객체의 속성이 변경되더라도 식별자가 동일하다면 같은 객체로 판단함.

```text
예) 회원, 주문, 상품
```

### Value Object

고유한 식별자보다 **객체가 가지고 있는 값 자체가 중요한 객체**임.

```text
예) 주소, 금액, 기간
```

### Aggregate

서로 관련된 Entity와 Value Object를 하나의 단위로 묶은 것임.

Aggregate 내부의 데이터 일관성을 유지하고 외부에서는 일반적으로 Aggregate의 대표 객체인 **Aggregate Root**를 통해 접근함.

### Repository

Entity 또는 Aggregate를 저장하고 조회하는 역할을 담당함.

DB 접근과 같은 데이터 저장 기술을 도메인 영역과 분리할 수 있도록 함.

### Domain Service

특정 Entity나 Value Object 하나에 포함시키기 어려운 **도메인 로직을 처리하는 서비스**임.

### Domain Event

도메인에서 발생한 의미 있는 사건을 표현함.

```text
예)
주문 완료
결제 완료
회원 가입 완료
```

다른 기능에서 해당 이벤트를 활용하여 후속 작업을 처리할 수 있음.

## 4. 모놀리식 아키텍처와 마이크로서비스 아키텍처

최근에는 서비스 규모가 커지고 기능별 독립적인 개발 및 배포의 필요성이 증가하면서 **마이크로서비스 아키텍처(MSA)**를 채택하는 조직이 증가하고 있음.

### 모놀리식 아키텍처(Monolithic Architecture)

하나의 애플리케이션 내부에 여러 기능을 함께 구성하는 방식임.

```text
하나의 Application
 ├─ 회원
 ├─ 주문
 ├─ 결제
 └─ 상품
```

### 마이크로서비스 아키텍처(Microservice Architecture)

하나의 큰 애플리케이션을 여러 개의 작은 서비스로 분리하고 각각 독립적으로 운영하는 방식임.

```text
회원 서비스
주문 서비스
결제 서비스
상품 서비스
```

### 비교

| 구분     | 모놀리식                   | 마이크로서비스(MSA)            |
| ------ | ---------------------- | ----------------------- |
| 구조     | 하나의 애플리케이션으로 구성        | 기능별 여러 서비스로 분리          |
| 개발     | 초기 개발이 비교적 단순함         | 서비스별 개발이 가능함            |
| 배포     | 전체 애플리케이션을 함께 배포       | 서비스별 독립 배포 가능           |
| 장애 영향  | 하나의 장애가 전체에 영향을 줄 수 있음 | 서비스 간 장애 격리가 상대적으로 용이함  |
| 확장     | 전체 애플리케이션 단위로 확장       | 필요한 서비스만 선택적으로 확장 가능    |
| 운영     | 상대적으로 단순함              | 서비스가 많아질수록 운영 복잡도가 증가함  |
| 통신     | 애플리케이션 내부 호출 중심        | 서비스 간 API 또는 메시지 통신 필요  |
| 적합한 경우 | 비교적 단순하거나 규모가 작은 시스템   | 규모가 크고 기능별 독립성이 필요한 시스템 |

MSA는 확장성과 독립적인 배포 측면에서 장점이 있지만, 서비스가 분리되면서 **네트워크 통신, 장애 처리, 데이터 관리, 배포 및 모니터링 등의 운영 복잡도가 증가할 수 있음.**

## 5. 이벤트 기반 아키텍처(Event-Driven Architecture)

이벤트 기반 아키텍처는 시스템에서 발생하는 **이벤트를 중심으로 기능을 연결하는 구조**임.

주요 구성요소는 다음과 같음.

* **Producer(생산자)** : 이벤트를 생성함.
* **Broker / Router(브로커 또는 라우터)** : 이벤트를 전달받아 적절한 소비자에게 전달함.
* **Consumer(소비자)** : 필요한 이벤트를 전달받아 후속 작업을 처리함.

동작 구조는 다음과 같음.

```text
Producer
   ↓
Event
   ↓
Broker / Router
   ↓
Consumer
```

생산자는 이벤트를 생성하여 Broker에 전달하고, Broker는 해당 이벤트에 관심이 있는 Consumer에게 이벤트를 전달함.

생산자와 소비자가 직접 연결되지 않아 서로에 대한 의존성을 줄일 수 있으며, 하나의 이벤트를 여러 기능에서 활용할 수도 있음.

예를 들어 주문 완료 이벤트가 발생하면 다음과 같이 활용할 수 있음.

```text
[주문 서비스]
     │
     │ 주문 완료 Event
     ↓
[Message Broker]
     │
     ├──→ [알림 서비스]
     ├──→ [배송 서비스]
     └──→ [통계 서비스]
```

따라서 이벤트 기반 아키텍처는 시스템 간 기능 연계뿐만 아니라 **알림 처리와 같은 비동기 작업에도 활용 가능함.**

## 6. CQRS 패턴

CQRS(Command Query Responsibility Segregation)는 **명령(Command)과 조회(Query)의 책임을 분리하는 패턴**임.

일반적인 시스템에서는 하나의 모델을 사용하여 데이터의 등록·수정·삭제와 조회를 모두 처리할 수 있음.

```text
하나의 Model
 ├─ 등록
 ├─ 수정
 ├─ 삭제
 └─ 조회
```

하지만 명령과 조회가 요구하는 데이터 구조가 서로 다른 상황에서도 하나의 모델을 사용하면 모델이 복잡해지고 코드 유지보수가 어려워질 수 있음.

특히 도메인이 복잡해질수록 이러한 문제가 증가할 수 있으며, 이를 해결하기 위해 CQRS를 사용할 수 있음.

CQRS에서는 다음과 같이 모델을 분리함.

```text
Command Model
 ├─ 등록
 ├─ 수정
 └─ 삭제

Query Model
 └─ 조회
```

### Command

시스템의 데이터를 변경하는 작업을 담당함.

```text
등록
수정
삭제
```

### Query

시스템의 데이터를 조회하는 작업을 담당함.

```text
목록 조회
상세 조회
검색
통계 조회
```

명령과 조회 모델을 분리하면 각각의 기능에 적합한 형태로 모델을 구현할 수 있음.

### 장점

* 명령과 조회 모델의 상호 영향을 최소화할 수 있음.
* 각 기능의 목적에 맞는 모델을 구성할 수 있음.
* 조회 모델을 별도로 최적화하기 용이함.
* 조회 데이터를 캐싱하는 등의 방법으로 조회 성능을 향상시키기 용이함.

### 단점

* 명령과 조회에 각각 모델을 구현해야 하므로 코드가 증가함.
* 단순한 시스템에서는 오히려 구조가 복잡해질 수 있음.
* 명령과 조회에 서로 다른 DB를 사용하는 경우 데이터 동기화가 필요할 수 있음.
* 시스템 구성 및 운영에 추가적인 작업이 발생할 수 있음.

따라서 CQRS는 모든 시스템에 적용하기보다는 **도메인이 복잡하거나 명령과 조회의 요구사항 및 성능 특성이 크게 다른 경우 적용을 고려하는 패턴**임.

## 전체 구조 요약

```text
MVC
→ 화면 요청 및 처리 역할을 Model / View / Controller로 분리

Layered Architecture
→ 애플리케이션을 역할에 따라 여러 계층으로 분리

DDD
→ 비즈니스 도메인을 중심으로 시스템을 설계

Monolithic
→ 하나의 애플리케이션으로 여러 기능을 구성

MSA
→ 기능을 여러 개의 독립적인 서비스로 분리

Event-Driven Architecture
→ 이벤트를 통해 시스템 및 기능을 연결

CQRS
→ 데이터 변경(Command)과 조회(Query)의 모델을 분리
```
